# AR4: Single observation sync

Parked 2026-09-25 by user direction; its visible benefit moves to
[batched admissions](incremental-send-recovery-and-admission-batching.md).
Retained for reference.

## Goal and scope

Move membership diffing and bounded reconcile/park policy from the KWin adapter into the portable Engine. One `sync` request should carry complete observations for all affected domains and return one plan, with removals before admissions, stable admission order, domain changes as remove plus admit, retained exception handling, and independent per-domain revisions, fingerprints, divergence and pending scope. Keep existing send/R4 acknowledgement and verification, fences, background adoption, placement-aware fitting, native focus/visibility behavior and correlated lifecycle summaries.

## Non-goals

No size-hint clamp acceptance, layout-policy seam, logical workspace model, transaction-model replacement, live KWin test, toolchain change, or edit to the dated architecture review.

## Approach and acceptance

- Establish existing foreground/background observation, reply and focus semantics before replacing adapter-derived admission/removal.
- Implement green slices across portable core, protocol wire/validation, and native observer/actuator, then retire dead adapter baselines and counters.
- Cover multi-window appearance, removal before admission, domain changes, flag transitions, drift/park, background domains, and in-flight send retention. Update byte-exact wire goldens and correlated lifecycle summaries.
- Verify workspace fmt/check/clippy/test, KWin typecheck/tests/build, `just check-portable`, and independent behavior review; report count and approximate TS line changes.

## Material decision

The existing adapter sends at most one membership command per round trip: `refreshForegroundNow` chooses the first new window in observation order, then chains later requests (`kwin/src/plan-adapter.ts:3071-3123`, `:6625-6662`). For a retained A followed by B and C together, the current route can display an intermediate A+B geometry before admitting C. Collapsing that intermediate write into one final plan is selected by the Orchestrator as a direct consequence of the user-requested review 7.7 ("one round trip and one Plan covering every affected domain"), reducing visible jank per `VISION.md`.

Preserve final admission order, native focus and desktop behavior, startup fitting, background anchors and independent per-domain state. Per-domain focus and revision reply fields are authorized in the combined reply because script and Planner ship from the same checkout; pin the change with byte-exact goldens (`crates/tiler-protocol/src/planner_protocol.rs:254-294`). Keep per-domain Sessions rather than merging them.

## Design-first checkpoint (candidate; independent review required before code)

The Orchestrator authorized a validated per-domain observation boundary, wire additions and domain-scoped pending checks. Proposed exact `sync` request shape: `{ "v": 1, "correlation_id": id, "owner": id, "generation": id, "command": { "op": "sync" }, "domains": [{ "domain": { "output": id, "workspace": id, "bounds": rect, "gap": int, "outer_gap": int }, "revision": int, "fingerprint": uint, "focused_window": id_or_empty, "windows": [{ "window": id, "output": id, "workspace": id, "rect": rect, "floating": bool, "fullscreen": bool, "maximized": bool, "sticky": bool, "fit_excluded": bool }] }] }`. Every field shown is required, including false flags; `domains` and `windows` are ordered and bounded, keys unique, and each window is homed on exactly its entry's domain. `fit_excluded` is the existing derived placement opt-out, not an exception flag. This payload contains the *current* native observation, including empty background domains; it contains no historical baseline or synthetic departure entry. Proposed exact reply shape: `{ "v": 1, "correlation_id": id, "outcome": "planned" | "partial" | "rejected", "domains": [{ "output": id, "workspace": id, "outcome": "planned" | "rejected", "kind"?: token, "message"?: text, "base_revision"?: int, "desired_geometry"?: [geometry], "desired_focus"?: focus_or_null }] }`; domain entries retain request order, successes include their final revision, final geometry and focus, failures include bounded rejection tokens and no geometry. `partial` requires independent successful domains; move-related source/target cannot be reported as independent successes if either half fails. Existing ops/replies remain unchanged until replacement. This addresses missing wire flags, global reply revision/focus and stale early-domain projections.

Fence order: existing same-UID D-Bus authorization **before** parsing; bounded bytes/JSON/strict DTO/version; shared correlation, owner and generation shapes; for each domain in request order check revision shape, unique opaque domain/window IDs, rectangles, gaps/inset/bounds, homing and focus membership; recompute its fingerprint over its entire *real* domain entry (domain geometry, focused ID, ordered member IDs/rectangles/all flags) and reject mismatch; decode `sync`; inspect each affected pending scope **before** `sync_binding` so send/R4 pending cannot be cleared on rebind; bind owner/generation; for each retained Session compare owner/generation and incoming domain revision/fingerprint against its accepted state, then apply Session's topology, completeness and lifecycle fences. A fresh domain starts at revision zero. One domain's fingerprint must never be reused for another. On accepted internal commits, the next step's revision must be the preceding verified Session revision, never a copied request revision. The input revision must first match the retained base and all intermediate revisions must remain linked to that accepted input by the verified commit chain. The input fingerprint must be checked against the incoming data before any work, then each step's fingerprint must describe its actual observed membership; never label a filtered observation with the unfiltered final fingerprint. This addresses the input-fence/fingerprint-copy failures and independent pending scope; existing ack/verify/status/cancel dispatch remains ahead of this route. The earlier window-count fence was retired by AR16.

Membership staging would use the *incoming* `windows` entries filtered in their original order for each step, with all flags and geometry preserved; remove every departure before admitting any arrival, retaining stable first-seen admission order. For a remove step, `Session::propose_remove` currently requires the removed window **in** its complete pre-removal observation (`session.rs:2079-2091`), while the proposed request has only the current post-removal observation and cannot supply that window by filtering. The existing adapter explicitly sends its **previous** snapshot for `remove` (`kwin/src/plan-adapter.ts:3084-3093`); manufacturing the missing member from a Session snapshot repeats the rejected synthetic-observation approach. Even with a previous native snapshot carried on the wire, it would require preserving a historical adapter baseline, contrary to AR4's baseline removal, and requires specifying how that snapshot is validated against the initial revision and fingerprint. A second `propose` after the first verified step requires an incremented revision (`reconcile.rs:517-520,1159-1160`); using the incoming base or final fingerprint for every intermediate step is invalid. This is an unresolved design constraint, **not** authorization to change Session completeness or transaction semantics. It addresses the prior fabricated-observation and stale-fence findings.

For each carried window, use all four flags as `ExceptionFlags`; an existing flag transition must pass through an explicit removal and (deferred or tiled) admission using real pre- and post-transition evidence, not a fail-closed permanent park. `fit_excluded` only gates near-strip fitting. Once observations are sound, fresh foreground and background domains use `try_flat_strip_fit` before `seed_session`, retain each domain's native focus or background anchor, and apply geometry/focus only after every domain has completed removal/admission. Work on per-domain clones; a refused domain must not roll back unrelated accepted domains, while a cross-domain move must avoid committing only one half. This addresses missing flag handling, fresh-start fitting, stale intermediate plans and cross-domain partial failure. The required pre-removal evidence and its fence semantics must pass independent review before implementation resumes.

## Current outcome

Scoping and the user-visible coalescing decision are complete. The first core approach only derived intents without committing geometry and counted observation changes rather than unsuccessful reconcile attempts. The replacement commits through Session, but independent review rejected it as a production foundation: sequential cross-domain commits can return a stale earlier plan; synthesized observations bypass real fingerprint/input fences and cross-domain removal can copy the target fingerprint into the source; global pending deferral collapses independent scopes; the current wire lacks explicit exception flags; fresh startup bypasses near-strip fitting. Both earlier semantic approaches failed and their experimental core diff was reverted.

A further single-domain core slice (reverted; not in the tree) passed core tests and portable checks, but independent review found that its per-step observations are assembled from the working session rather than the complete carried observation, its input has no request revision or fullscreen/maximized/sticky flags, and its global pending guard blocks independent domains. It also bypasses the existing retained-session retirement/rebuild behavior. This repeats the prior input-fence failure, so the slice is **not accepted** and must not be wired into protocol or KWin. Passing tests were not acceptance.

Design review outcome: an independent Worker rejected the post-only candidate. `Session::propose_remove` requires a complete *pre-removal* observation containing the departing window (`session.rs:2079-2091`), which cannot be filtered out of a current native snapshot that no longer contains it. The existing adapter sends a previous snapshot specifically for removal (`kwin/src/plan-adapter.ts:3084-3093`). A two-evidence request with an authenticated historical snapshot retains an observation baseline and needs additional revision/fingerprint validation; post-only removal instead requires a change to Session's completeness/fence semantics. Cross-domain move atomicity and fingerprint derivation for intermediate membership sets also remain unresolved.

Stop before implementation: the requested sync with removal of adapter baselines cannot satisfy the current Session removal fence using only current observations. Recommendation to the Orchestrator: defer full AR4 behind AR11 transaction-model work or explicitly revise the evidence/baseline requirement and design a validated two-evidence request. Neither alternative is approved by this note. Keep the note active and update the `docs/decisions.md` adapter-baseline entry only when a replacement actually ships.

Keep this note active until AR4 passes acceptance and can be archived.
