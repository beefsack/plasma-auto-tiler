## Shortcut profile routes

Verified against **KWin v6.7.5** upstream [`scripting.h`](https://raw.githubusercontent.com/KDE/kwin/v6.7.5/src/scripting/scripting.h) and [`scripting.cpp`](https://raw.githubusercontent.com/KDE/kwin/v6.7.5/src/scripting/scripting.cpp): the JavaScript `Script` exposes `registerShortcut` and no `unregisterShortcut` or binding-update call. Registration creates a script-owned `QAction`, calls `KGlobalAccel::setShortcut`, and connects its trigger to the callback. `registerShortcut` returning true means the callback was callable, **not** that the chord is conflict-free or delivered. KWin's [QML `ShortcutHandler`](https://raw.githubusercontent.com/KDE/kwin/v6.7.5/src/scripting/shortcuthandler.h) describes its sequence as construction-only; adopting that separate script type is not an in-place JS rebind.

| Route | Cost and user-visible consequence |
| --- | --- |
| Register union of all profile actions once; live callback dispatch | No unregister/lifecycle dependence. Different-profile chords remain active KGlobalAccel registrations even while their profile is inactive; they appear in global shortcut settings and can shadow other apps. Currently all profiles share one catalog, so union is identical today; meaningful future profiles need chord/conflict policy before this is useful. The existing five-row foreign-override journal cannot silently cover new conflicts. |
| Use native KGlobalAccel from script KCM/effect | Existing effect KCM already has a read/verified-write KGlobalAccel D-Bus backend (`shortcutreconciler.h:36-56`). Rebinding *existing project actions* after Save is technically plausible but needs an atomic, validated profile transition and interaction with user-customized bindings. Registering effect-owned actions instead introduces a second lifecycle owner and dependence on effect availability, contrary to the script page working without the effect. New foreign-conflict writes require explicit user-approved rows and reversible journal handling; no automatic foreign mutation on Save. |
| Unload/load script through `/Scripting` | Re-registers one selected profile, not a union, but is asynchronous and tears down every controller, not just shortcuts. Shortcut records may persist after unload without a live callback (`docs/live-kwin-testing.md:82-84`); inspect exact action tuples and callback behavior, not just `isScriptLoaded`. Does not resolve conflicts or journal ownership automatically. |

Recommendation for research direction: retain script ownership; first decide whether the three named profiles should have distinct behavior/chords. If yes, investigate a bounded project-action rebinding path using the existing native KCM KGlobalAccel transport with pre/post readback and no foreign edits; avoid registering inactive chords or effect-owned actions by default. The current conflict journal remains explicitly operated by its effect KCM and is **not** a profile migration ledger.

## Workspace mode and script reload

`kwin/src/workspace-native.ts:408-447,481-518,801-985,1184-1360` owns an in-memory native-desktop mapping, output associations and displaced-workspace history. Local and global-unique modes assign distinct backing desktops to output domains; shared uses the same backing-desktop list on each output (`docs/decisions.md:551-597`). The mode is consumed on `enable` only. `disable` clears mapping/displacement memory, not native desktops; script destruction also loses the `owned` set that distinguishes desktops this instance created from adopted ones. Existing windows have actual KWin desktop/output membership, and Rust retains topology by logical domain; reassigning a native desktop to a new output/domain is not a mere settings reread. A switch needs rules for logical numbering, window/workspace placement, layouts and shares, occupied/displaced/empty backing desktops, visible workspace and focus. None is selected for a runtime transition.

KWin v6.7.5 exposes public `/Scripting` `loadScript`, `unloadScript`, `isScriptLoaded` and per-script `run`/`stop` (same upstream `scripting.h/cpp`). `unloadScript` and D-Bus `stop` schedule `deleteLater`; `loadScript` returns `-1` while the old instance is still listed, and `run` starts file evaluation asynchronously. Thus a KCM cannot safely treat a queued reconfigure or an immediate unload/load pair as an applied-settings acknowledgement. Importantly, the production entry (`kwin/src/entry.ts:55-56`) discards the returned `planHandle` without calling its JS `stop`; KWin's `deleteLater` does **not** invoke that JS method. An explicit project teardown path exists (`kwin/src/plan-adapter-entry.ts:4708-4748`) but is not wired to D-Bus unload. If called, disabling a planned send reports one best-effort `adapter-lost` and can still leave uncertain native mutation (`kwin/src/workspace-send-adapter.ts:1087-1121`). A controlled reload would need a quiescent/explicit teardown protocol, identity preconditions, verified destruction, exact source/path binding, run/readiness and recovery checks. Current public lifecycle queries do not prove source identity or handler absence (`docs/live-kwin-testing.md:43-57`).

**Retained-layout correction:** the Planner is a separate process retaining `Session`s across requests (`crates/plasma-auto-tiler/src/planner_service.rs:132-170`, `crates/tiler-protocol/src/planner_protocol.rs:2175-2207`). It discards sessions when owner or generation changes (`crates/tiler-core/src/engine.rs:151-171`), or on an unusable/mismatched domain. Production `kwin/src/entry.ts:55` hardcodes `owner: "kwin-plan-adapter", generation: "plan-1"`; merely unloading/reloading the script **does not change this binding**. With a surviving Planner and matching domains, topology may survive; after remapping, mismatched domains can be discarded/reseeded, and pending operations can remain fenced. Neither layout preservation nor fresh adoption is guaranteed by reload today. A deliberately new generation plus a proved idle/terminal-pending rule and fresh current-window adoption would be a new design, potentially losing split/group/share history. Live workspace-mode reload must not be used as a generic post-Save mechanism without that product choice.

## Decisions to request

1. Should `shortcutProfile` acquire distinct chord/behavior catalogs? Recommended: decide the catalogs before engineering profile switching; the three current options are identical.
2. If chords differ, may a profile Save rebind only the project's existing action records with exact readback while foreign conflicts remain explicit Apply/Revert? Recommended: yes, subject to an offline feasibility/protocol check; no inactive-profile shortcut registrations.
3. On `workspaceMode` switch, should native desktops/windows keep their current membership and the tiler fresh-adopt current eligible windows, accepting possible layout loss and a defined focus/view rule, or must existing topology and output/displacement associations be preserved? Recommended smallest initial *candidate*: quiesced fresh adoption without native window moves, **only after** user specifies layout-loss and focus semantics and a safe Planner generation transition is designed.
4. Is an explicit controlled reload acceptable only for chosen changes with a verified idle/source/restore boundary? Recommended: do not use it as an automatic generic post-Save route; it is not a guaranteed layout reset or callback proof.
